# Competition Rules Intake

建立一份可追溯的规则底稿，使后续写作、工程验证和提交检查都以同一组要求为准。

## 输入

接受以下任意组合：

- 赛事官网通知、赛题说明、评分办法、提交模板和附件。
- 学校或指导教师转发的通知。
- 往届材料，但必须标为“参考”，不能自动视为本期有效。
- 现有项目目录和输出物清单。

若用户只想写正文而没有官方材料，先完成可写部分，同时明确列出哪些规则仍待官方核验。

## 来源优先级

按以下顺序解决冲突，并保留冲突记录：

1. 本期官方赛事通知与官方附件。
2. 本期官方平台页面、FAQ 或组委会书面答复。
3. 学校、学院或指导教师针对本期发布的补充要求。
4. 往届官方模板和样例。
5. 二手文章、聊天截图或经验总结。

不得把发布日期、页数、字数、匿名要求、文件命名或评分比例从往年直接套用到本期。

## 工作流

### 1. 固定核验范围

记录赛事全名、赛道、组别、适用年度、作品类型和提交主体。若同一赛事存在校赛、省赛、国赛或不同赛道，分别建模，不合并规则。

### 2. 建立来源台账

对每个来源记录：

| ID | 标题 | 发布者 | 日期/版本 | URL 或本地路径 | 来源级别 | 获取状态 |
|---|---|---|---|---|---|---|

“获取状态”使用 `已取得原件`、`仅见摘要`、`链接失效` 或 `待确认`。下载文件保留原文件名，并在台账中记录哈希或文件大小，防止后续误用版本。

### 3. 提取原子要求

每条要求只表达一件事，并分配稳定的 ID，例如 `R-001`。建议字段：

| ID | 类别 | 原文要求 | 精确来源 | 硬性/建议 | 截止时间 | 验收证据 | 负责人 | 状态 |
|---|---|---|---|---|---|---|---|---|

优先提取：

- 资格、团队、报名和知识产权要求。
- 赛题范围、必须实现项和禁止项。
- 文档模板、页数/字数、匿名、签名、日期和命名规则。
- 源码、工程、可执行程序、视频、截图和附件的交付要求。
- 技术验收方式、现场演示、答辩和复现条件。
- 评审维度、权重和必须突出的证据。
- 提交平台、文件大小、编码格式和截止时区。

将解释性意见放入单独备注，不混入“原文要求”。

### 4. 处理冲突与缺口

同一事项出现不同说法时：

1. 保留两条记录和各自来源。
2. 标明采用哪条、理由和影响。
3. 只在使用者确认或找到明确更新来源后关闭冲突。
4. 影响资格、截止时间、模板或评分的未决项必须升级为阻断项。

### 5. 建立要求到材料的映射

| 要求 ID | 将写入的章节/文件 | 工程证据 | 当前缺口 | 完成判定 |
|---|---|---|---|---|

工程证据应能定位到具体命令输出、报告、日志、源文件、测试记录或现场演示。计划、设想和未执行结果不能作为“已满足”证据。

### 6. 输出评审包

至少生成：

- `rules_source_ledger.md`：来源、版本和核验状态。
- `requirements_matrix.md`：原子要求、负责人和证据映射。
- `conflicts_and_open_questions.md`：冲突、缺口和需向组委会确认的问题。
- `submission_checklist.md`：可从模板直接执行的提交前清单。

如只需要一个文件，可将四部分合并，但标题和信息字段必须保留。

## 停止条件

遇到以下情况时暂停依赖该规则的结论，并向用户给出具体待确认项：

- 只能取得摘要，无法查看官方原件或附件。
- 本期与往期模板存在实质差异。
- 资格、截止时间、提交方式或必交文件互相矛盾。
- 官方页面要求登录后才能取得关键附件，而当前无访问权限。
- 只有二手信息支撑一条高风险硬性要求。

其他可独立推进的内容继续完成，不因单个疑问停止全部工作。

## 完成判定

- 每条硬性要求都有来源、状态、负责人和证据入口。
- 每条关键结论都能回到原始页面、文件或附件。
- 往届材料均被显式标记为参考。
- 未确认内容没有被写成已满足。
- 输出的清单可用于下一阶段的 `evidence-driven-engineering-report` 和 `submission-package-audit`。
